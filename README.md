# Сервис генерации

Сервис списывает токены за генерацию, выполняет её через подходящие ноги модели и
возвращает стоимость, если выполнить задачу не удалось. В комплекте — PostgreSQL
и два настраиваемых фейковых провайдера, `alpha` и `beta`.

## Запуск

```bash
docker compose up --build -d
```

Миграции применяются автоматически перед запуском приложений. API работает в
четырёх процессах. Документация API: <http://localhost:8000/docs>, провайдеров:
<http://localhost:8001/docs> и <http://localhost:8002/docs>.

В каталоге уже есть `image-fast` за 2 токена и `video-long` за 25 токенов с ногами
из задания. Пользователь создаётся с нулевым балансом при успешном платеже.
Пример подписанного начисления и заказа:

```bash
docker compose exec -T api python - <<'PY'
import hashlib
import hmac
import json
import os
from uuid import uuid4

import httpx

body = json.dumps({
    "payment_id": str(uuid4()), "user_id": 1,
    "tokens": 100, "status": "completed",
}).encode()
signature = hmac.new(
    os.environ["WEBHOOK_SECRET"].encode(), body, hashlib.sha256,
).hexdigest()
with httpx.Client(base_url="http://localhost:8000") as client:
    payment = client.post("/webhooks/payments", content=body, headers={
        "Content-Type": "application/json", "X-Signature": signature,
    })
    payment.raise_for_status()
    task = client.post("/generate", json={
        "user_id": 1, "model_slug": "image-fast",
        "prompt": "A quiet street in watercolor", "ref_images": [],
    })
    task.raise_for_status()
    print(task.json())
PY
```

Статус и история: `GET /tasks/{task_id}`; баланс и последние 25 операций:
`GET /users/1/balance`. Успешный платёж имеет статус `completed`; `pending` и
`failed` не начисляют токены. Подпись обоих видов вебхуков — hex HMAC-SHA256
сырого тела в `X-Signature`, секрет берётся из `WEBHOOK_SECRET`.

Параметры окружения можно задать в `.env` по примеру `.env.example`.
`PROVIDER_TIMEOUT` по умолчанию равен 60 секундам. Данные сохраняются в Docker volume.
Остановка: `docker compose down`.

Режим провайдера задаётся через `POST /settings` на порту 8001 или 8002:
`failure_rate`, `error_type`, `sync_error` (`none`, `503`, `timeout`),
`sync_timeout_seconds`, `delay_seconds`, `duplicate_count`,
`concurrent_duplicates`, `drop_webhook`. Настройки действуют на новые задания.
Без заданной задержки вебхук приходит через 2–20 секунд; задержка больше
`PROVIDER_TIMEOUT` воспроизводит поздний результат. Доставки повторяются при
недоступности получателя.

## Миграции

Повторное применение и просмотр текущей версии:

```bash
docker compose run --rm migrate alembic upgrade head
docker compose run --rm migrate alembic current
```

Для следующей миграции создать файл в локальной папке `migrations/versions`:

```bash
docker compose run --rm --user "$(id -u):$(id -g)" \
  -v "$PWD/migrations:/app/migrations" migrate \
  alembic revision -m "describe schema change"
```

Заполнить `upgrade()` и `downgrade()`, затем пересобрать образ и применить:

```bash
docker compose build migrate
docker compose run --rm migrate alembic upgrade head
```

## Тесты

```bash
docker compose --profile tests build tests
docker compose --profile tests run --rm tests
```

Тесты обращаются по HTTP к приложению с четырьмя воркерами и проверяют настоящий
PostgreSQL. Покрыты четыре обязательных сценария: 20 одновременных повторов
оплаты, 10 отказов на последней ноге с единственным возвратом, переход на вторую
ногу и поздний `completed` после сторожа. Дополнительно проверяются лимит активных
задач, правила ошибок, подписи, восстановление отправки и откат транзакции.
Настройки фейковых провайдеров временно меняются на время тестов и восстанавливаются.

## Единственность операций и падения процессов

Каждый финансовый эффект записывается в журнал и изменяет баланс в одной
транзакции. Уникальный `payment_id` запрещает повторное начисление; уникальная
пара `(task_id, kind)` запрещает повторное списание или возврат. Строка пользователя
блокируется перед проверкой баланса и числа активных задач, поэтому параллельные
запросы не обходят ограничения. Баланс равен сумме знаковых сумм журнала.

Вебхук, синхронный отказ и сторож используют общий переход состояния.
Порядок блокировок — пользователь, задача, попытка. Состояние попытки и текущий
идентификатор проверяются под блокировкой; завершённые попытки повторно не применяются.

При падении процесса до коммита PostgreSQL откатывает всю транзакцию. После
коммита повторный вебхук не меняет баланс. Отправки сохраняются в таблице попыток
вместе с заказом и списанием. Воркеры забирают их через `FOR UPDATE SKIP LOCKED`
с ограниченным сроком владения; после падения работу подхватит другой процесс.
HTTP-запрос выполняется вне транзакции. При повторной отправке используется тот
же `Idempotency-Key` — идентификатор попытки; фейковый провайдер хранит его в БД
и возвращает прежний `external_id`. Маркер владения защищает от устаревшего ответа
отправителя. Если ответ провайдера приходит до сохранения `external_id`, вебхук
сопоставляется по подписанному `attempt_id`.

## Поздний результат

Если сторож уже зафиксировал таймаут попытки, её поздний `completed` игнорируется,
даже когда следующая нога ещё работает. После окончательной неудачи задача
остаётся `failed`, результат не сохраняется, повторного возврата нет. Если
вебхук и сторож приходят одновременно, применяется переход, первым получивший
блокировки и зафиксировавший транзакцию. Поэтому задача не получает одновременно
результат и возврат токенов.
